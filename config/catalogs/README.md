# Makino working catalogs

These directories are working space for administrator-authored imports and
exports, not a second copy of the server's defaults. Makino uses
`config/catalogs/<catalog>` as its default input directory when neither `--file`
nor `--dir` is provided, relative to its working directory. Supported catalog
names are `notice`, `shop`, `exchange`, `gacha`, and `gacha-rules`.

Initialization seeds remain in `internal/db/internal/migration/catalogdata/`
and use the same category folder names:

```text
internal/db/internal/migration/catalogdata/
├── notice/       # notice_catalog.yaml and showcase_shop_notice.yaml
├── shop/         # shops.yaml, normal_items.yaml, dia_items.yaml, login packs, ...
├── exchange/     # exchange.yaml
├── gacha/        # gacha_catalog.yaml
└── gacha-rules/  # gacha_rules.yaml
```

These are the single source for initial catalog data. Other initialization and
gameplay YAMLs stay in their existing locations. The seeds are bundled with the
server, and level-1 initialization loads them into MongoDB.
Existing installations receive only missing gacha configuration and the old
showcase notice field; their other catalogs are not replaced. Runtime requests
read MongoDB, not either YAML directory. Cleared catalogs remain cleared across
restarts, and changing a seed does not affect an initialized database.

## Build and connection settings

```sh
go build -o makino ./cmd/makino
./makino --help
./makino server --help
```

The binary loads `.env` from its working directory. User commands use
`SOLIS_ADMIN_AUTH` and the HTTP admin server at `http://localhost:50052`.
Set `MAKINO_SERVER_URL` or pass `--server URL` **before** `user` to override it.
Use HTTPS for a remote admin server. Catalog commands use `SOLIS_DB_USERNAME`
and `SOLIS_DB_PASSWORD`, with optional `SOLIS_DB_HOST`/`SOLIS_DB_PORT`
(defaults: `localhost:27017`). They do not require the game server to be running
and never run database migrations.

```sh
./makino user create --id ABCD1234 --suid 11111111-1111-1111-1111-111111111111
./makino user god --id ABCD1234 --message enjoy --fan all --bond all
./makino user delete --id ABCD1234
```

Create prints the resulting user ID and password. Omitted creation values are
generated by the admin API. Keep that output private; passing `--password` may
also leave the password in shell history.

## Edit running catalogs

Use the matching seed folder to locate the original definitions. Some seeds are
initializer fragments, not standalone Makino import documents: shop metadata,
item lists, and login packages are separate, and the showcase notice belongs
under `showcaseShopNotice` in a notice import. To edit an existing server, export
its current catalog first. Export combines the correct structure and preserves
any administrator changes and diamond-product mappings.

```sh
./makino server notice --export > config/catalogs/notice/catalog.yaml
# Edit the exported file, then import from the default directory:
./makino server notice --overwrite
# Explicit paths remain supported:
./makino server notice --add --file one-notice.yaml
./makino server notice --overwrite --dir ./server-notice
./makino server notice --clear

./makino server shop --export > shops.yaml
./makino server shop --overwrite --file shops.yaml
./makino server exchange --export > exchanges.yaml
./makino server exchange --overwrite --file exchanges.yaml
```

For notice/shop/exchange, `--dir` imports `.yaml` and `.yml` files recursively in
sorted order, with multiple YAML documents supported. `--add` upserts complete
entries by ID and preserves other entries. For a shop, an entry includes both
its metadata and item list; adding an item means editing that list. `--overwrite`
replaces the entire catalog. Invalid input leaves the database unchanged.
`--clear` is explicit; an empty directory or document cannot erase a catalog.

Shops remain free of real-money purchases and purchase limits. Preserve the
exported `originalProductIds` field for converted bundles, because it supplies
their diamond contents. `showcaseShopNotice` in the notice catalog controls the
shared goods-shop notice; clearing it uses the client's safe dummy notice.

## Add an item to the normal shop

Export the complete current shop catalog:

```sh
./makino server shop --export > config/catalogs/shop/catalog.yaml
```

In that file, find the shop with `shopId: shop_top_shop`. Append the following
entry to **its existing `items:` list**, keeping the other entries and all shop
metadata intact. This example adds a free bundle of 160 blue diamonds using an
existing thumbnail:

```yaml
- id: shop_item_custom-blue-dia-160
  name: ブルーダイヤ×160（追加）
  thumbnailAssetId: img_shop_item_thumb_blue-dia-120
  rewardId: "rd_auto;paid_stone;;160"
  consumptionId: ""
  unlocked: true
  order: 1000
```

Import the edited file and reopen the shop in the client:

```sh
./makino server shop --overwrite --file config/catalogs/shop/catalog.yaml
```

An empty `consumptionId` makes the item free. For a price, use an existing
Consumption master ID. The item ID must be unique across all shops. Do not send
only the new item with `--add`: that operation upserts complete shop entries,
not individual items. Keep `originalProductIds` unchanged for existing bundles.

## Select ongoing gachas

```yaml
useMasterCatalog: false
ignoreOfficialDates: true
gachaIds:
  - gacha-normal-26-0718
  - gacha-birthday-26-0913
```

```sh
./makino server gacha --overwrite --file rotation.yaml
./makino server gacha --export
./makino server gacha --clear
./makino server gacha-rules --export > gacha-rules.yaml
./makino server gacha-rules --overwrite --file gacha-rules.yaml
```

Gacha and gacha-rules imports each take one YAML document. `gachaIds` references
the installed master data. With `useMasterCatalog: false`, these are the exact
selected gachas. With `true`, the usual automatic selection remains and the
explicit IDs add extra gachas. `--add` appends IDs while preserving the current
automatic-selection and date settings.

`ignoreOfficialDates` applies only to explicit IDs. It permits reopening old
gachas but keeps tickets, resources, draw limits, and other unlock requirements.
Historical item/toy gachas also need their reward pools in `gacha-rules`.
Rules control rarity weights, guarantees, special reward pools, and notice
aliases. Normal card gachas keep equal probabilities within each rarity tier.

Changes take effect on the next API request; a client may need to reopen its
page. Already-running draws finish using their transaction's configuration.
